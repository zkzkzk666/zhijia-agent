# 功能安全 ISO 26262

## 什么是功能安全

- 目标：消除由**系统/电子电气**故障（系统性故障、随机硬件故障）导致的不合理风险。
- 覆盖：产品开发全生命周期（概念 → 系统 → 硬件 → 软件 → 生产/运维）。

## 核心流程

1. **概念阶段**：相关项定义 → 危害分析与风险评估（HARA）→ 安全目标与 ASIL。
2. **系统级**：技术安全概念、系统架构、安全需求分配。
3. **硬件级**：硬件架构度量、随机硬件失效指标（PMHF/SPFM/LFMF）、FMEDA。
4. **软件级**：软件安全需求、架构/单元设计与测试、工具置信度（TCL）。
5. **集成与验证**：验证计划、测试、失效注入（FIT）、确认措施。
6. **生产与运行**：生产控制、维护、售后安全相关事件反馈。

## HARA 与安全目标

- **HARA**：分析整车在场景中的危害事件 → 通过 S（严重度）/E（暴露率）/C（可控性）定级。
- **ASIL**：A/B/C/D 四级（D 最高），QM 为非安全相关。由 S/E/C 组合查表得到。
- **安全目标示例**：避免整车在可通行场景中因纵向误加速导致碰撞（ASIL C/D）。

## 常用方法

- **FMEA**：自下而上，分析失效模式对系统的影响。
- **FTA**：自上而下，分析导致顶层危险的原因组合。
- **FMEDA**：硬件定量可靠性分析与失效度量。
- **安全机制**：诊断覆盖（如 E2E 校验、看门狗、冗余表决、故障记忆）。

## ASIL 分解与继承

- 安全目标可分解到冗余通道（如 D → C(D)+C(D)），用于降低单通道要求。
- 分解后仍需保留独立性论证（避免共因失效）。

## 与 SOTIF 的关系

- ISO 26262 针对**电子电气故障**；ISO 21448（SOTIF）针对**无故障但功能/性能不足或场景误用**，两者互补。

## 工程落地要点

- 需求到代码的可追溯性；安全需求与普通需求分离管理。
- 软件安全架构采用分层/分区，关键模块独立部署、独立监控。
- 工具链置信度评估：对生成代码/自动化工具做 TCL1/TCL2/TCL3 分类与验证。
